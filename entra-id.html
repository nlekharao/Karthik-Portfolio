01 · ENGINEERING CHALLENGE

Modernizing authentication across 70+ production applications

The project involved moving a large portfolio of enterprise applications from legacy SiteMinder authentication to Microsoft Entra ID without disrupting access to business-critical systems.

The application estate consisted of .NET and .NET Core applications with existing authentication dependencies and different integration requirements. The migration therefore needed to address both the identity-platform change and the corresponding application-side engineering required to adopt the new authentication model.

The core migration team consisted of just three engineers, making repeatability and standardization important to delivering the migration across the application portfolio.

02 · TARGET AUTHENTICATION ARCHITECTURE

Decoupling application authentication from the identity provider

Rather than embedding Entra-specific authentication handling independently within every application, the target design introduced a reusable middleware layer between the application request pipeline and Microsoft Entra ID.

This gave applications a common authentication pattern while keeping the identity-provider interaction largely abstracted from individual application functionality.

03 · REUSABLE SSO MIDDLEWARE

Abstracting Entra ID from the application layer

Implementing the complete authentication flow independently across dozens of applications would have created repeated code and inconsistent integration patterns.

Reusable authentication middleware was developed to provide a common integration layer across the .NET and .NET Core application portfolio. Once integrated, the middleware participated in the application's request pipeline rather than requiring application functionality to explicitly invoke authentication functions.

When authentication was required, the middleware initiated the redirect to Microsoft Entra ID. Following successful authentication, Entra redirected the user back to the application with the returned token.

The middleware processed the authentication response, extracted the required user information and persisted the returned Entra token in a cookie so the authenticated context could be maintained within the application.

Token refresh was intentionally not handled as a separate middleware function. When the token expired, the user was routed through the Entra authentication flow again.

Middleware Responsibilities
Detect authentication requirement
Redirect to Microsoft Entra ID
Process returned token
Extract user information
Persist token in cookie
Return authenticated context to application
On token expiry, authentication is initiated again rather than performing a separate token-refresh flow.
04 · IDENTITY & SECRETS CONFIGURATION

Configuring the identity platform behind the application flow

The middleware-based application integration was supported by Microsoft Entra ID configuration for application identities, provisioning and enterprise access controls. Client secrets required for the integrations were stored in AWS Secrets Manager rather than embedded in application code or configuration.

05 · APPLICATION INTEGRATION & EDGE CASES

Applying a common pattern without assuming every application was identical

The reusable middleware provided a standard authentication pattern, but migration still required understanding each application's existing authentication flow, dependencies and integration behaviour.

Application-specific configuration and engineering changes were made where required while retaining the common authentication model wherever possible.

Engineering Edge Case

Third-party redirect causing anonymous authentication

One application included a third-party integration whose redirect behaviour resulted in an anonymous-authentication condition. The application therefore required additional handling around the redirect flow while still integrating with the common authentication middleware.

06 · MIGRATION & CUTOVER

Moving production authentication without disrupting users

Authentication is a critical application dependency: a migration failure can make an otherwise healthy application inaccessible. Applications were therefore migrated incrementally rather than treating the entire portfolio as a single production cutover.

Each application was assessed to understand its existing authentication flow and integration requirements. The target integration was then prepared, authentication scenarios validated, and the application moved to the new authentication model.
