01 · ENGINEERING CHALLENGE

Modernizing authentication across 70+ production applications

How do you change the authentication foundation of a large application portfolio without disrupting users?

More than 70 enterprise applications had to be transitioned from SiteMinder authentication to Microsoft Entra ID without disrupting access to production systems used across the insurance business.

The applications were built on .NET and .NET Core and had existing authentication and authorization dependencies. This was therefore not simply an identity-platform configuration exercise — individual applications also had to be changed to operate with the new authentication model.

With a three-person core engineering team working across the portfolio, repeatability mattered. Common authentication behaviour was implemented through reusable middleware rather than engineered independently for every application.

02 · AUTHENTICATION ENGINEERING

Re-engineering the application's authentication path

Moving from SiteMinder meant changing how each application participates in authentication.

Reusable authentication middleware was developed to provide a consistent integration path between the applications and Microsoft Entra ID.

The middleware is a permanent part of the runtime authentication path. When a user begins a new session, it participates in the authentication flow, redirects the user to Microsoft Entra ID when authentication is required and processes the authentication response returned to the application.

User information is extracted from the returned authentication response and the token is persisted in a cookie so that an authenticated application session can be established.

A separate token-refresh mechanism was not implemented. When the token expires, the user is sent through authentication again.

03 · APPLICATION ENGINEERING

What changed inside the applications

The migration required application code changes — not just Entra configuration.

Existing SiteMinder-dependent authentication behaviour had to be replaced or adapted so that each application could operate through the new authentication path.

Applications also had to consume the authenticated user information supplied through the new integration and maintain the appropriate authenticated application context.

Authorization was not left entirely unchanged. Existing application role and access behaviour required some code changes so that authorization continued to work correctly with the identity established through Entra.

Application-Level Changes
Authentication Integration Adapt the application from its existing SiteMinder-dependent authentication path to the reusable Entra authentication flow.
User Context Consume authenticated user information returned through the new identity flow.
Session Handling Establish and maintain the authenticated application session using the returned authentication information.
Authorization Modify existing role and access handling where required to work with the new authenticated identity.

04 · IDENTITY PLATFORM CONFIGURATION

Connecting applications securely to Microsoft Entra ID

Application engineering and identity configuration had to work together.

Each migrated application required the corresponding identity configuration in Microsoft Entra ID so that it could participate securely in the new authentication model.

This included application registrations, service principals and user/group provisioning, alongside enterprise identity controls such as MFA, Conditional Access, RBAC and Zero Trust principles.

Client secrets required by the application integrations were stored in AWS Secrets Manager rather than embedded directly in application code.

05 · PRODUCTION MIGRATION

Migrating application by application

A portfolio of 70+ production applications could not be treated as one authentication cutover.

Applications were migrated individually so that the required code changes, identity configuration and authentication behaviour could be tested and validated before each production transition.

Applications that aligned closely with the standard pattern could follow the repeatable migration approach directly. Applications with additional dependencies required more application-specific engineering.

This was particularly important where existing integrations behaved differently under the new authentication flow.

06 · ENGINEERING RESULT

A repeatable authentication architecture across the portfolio

Common authentication engineering could be reused without treating every application as an identical migration.

The final approach combined reusable runtime authentication middleware, application-specific engineering and enterprise identity configuration.

Common authentication behaviour did not have to be independently engineered for every application, while individual applications could still be adapted where their authorization logic or external dependencies required different handling.

This provided a practical path for transitioning a large application portfolio from SiteMinder to Microsoft Entra ID while maintaining continuity across production systems.
