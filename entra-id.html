01 · ENGINEERING CHALLENGE

Modernizing authentication across 70+ production applications

More than 70 enterprise applications had to be transitioned from SiteMinder authentication to Microsoft Entra ID without disrupting access to production systems used across the insurance business.

The applications were built on .NET and .NET Core and had existing authentication and authorization dependencies. The challenge was therefore not simply an identity-platform configuration exercise: individual applications also had to be adapted to work correctly with the new authentication model.

With a three-person core engineering team working across a large application portfolio, repeatability was important. A reusable authentication middleware approach allowed common authentication behaviour to be engineered once and used across the migrated applications.

02 · AUTHENTICATION ENGINEERING

Re-engineering how applications authenticate users

Migrating an application meant changing how it participated in authentication — moving from its SiteMinder-based authentication path to an application flow integrated with Microsoft Entra ID.

From SiteMinder to an Entra-based application flow

Each application had to be adapted so that a new user session could be routed through the Entra authentication flow, the returned authentication information could be processed, and the authenticated user's identity could be made available to the application.

Authentication Model
Before · SiteMinder Applications operated with their existing SiteMinder-based authentication dependencies and identity handling.
→
After · Microsoft Entra ID Applications were adapted to use the new authentication flow, reusable middleware and Entra-authenticated user context.

Reusable authentication middleware

Rather than implementing the same authentication behaviour independently across more than 70 applications, reusable middleware was developed to provide a consistent integration path between the applications and Microsoft Entra ID.

The middleware remains part of the runtime authentication path. When a user starts a new session, it participates in the authentication flow and handles the interaction required to establish an authenticated application session.

Runtime Authentication Flow
User Starts a new application session
→
Authentication Middleware Detects authentication requirement and initiates redirect
→
Microsoft Entra ID Authenticates the user and returns the authentication response
→
Middleware + Application Processes returned identity and establishes authenticated context
Entra response → token processing → user information extracted → token persisted in cookie → authenticated application session

Authentication Redirect

The middleware participates in the application authentication path and redirects users to Microsoft Entra ID when a new authentication is required.

Token Processing

After authentication, the response returned by Entra is processed and user information is extracted for use by the application.

Session Handling

The returned token is persisted in a cookie so that the authenticated application session can be maintained.

Re-authentication

A separate token-refresh mechanism was not implemented. When the authentication token expires, the user is sent through the authentication flow again.

What changed inside each application

The migration also required application-level changes. Existing authentication dependencies had to be replaced or adapted so that the application could participate in the Entra authentication flow and consume the authenticated user context provided through the new integration.

Authorization was not simply left untouched. Some application code also had to be changed so that existing roles and access behaviour continued to work correctly with the identity supplied through the new authentication model.

Authentication Integration

Application authentication behaviour was modified to move from the existing SiteMinder-dependent flow to the reusable Entra authentication path.

User Context

Applications were adapted to consume the user information established after successful Entra authentication.

Authorization Changes

Existing application authorization and role-handling code required changes to work with the new authenticated identity.

Application Configuration

Each application required the configuration needed to connect its authentication flow with its corresponding Entra application identity.

04 · PRODUCTION MIGRATION

Migrating applications without a portfolio-wide cutover

The 70+ applications were migrated application by application rather than through a single portfolio-wide authentication cutover. This allowed each application's integration to be implemented, tested and validated independently.

Application-specific exception

One application included a third-party integration whose redirect behaviour resulted in an anonymous-authentication condition. The standard migration approach therefore required application-specific handling for that integration.

05 · ENGINEERING RESULT

A reusable authentication architecture across 70+ applications

The migration combined application engineering with enterprise identity configuration. Rather than treating each application as an independent authentication implementation, common authentication behaviour was encapsulated in reusable middleware that remains in the runtime authentication path of the migrated applications.

This created a repeatable approach for migrating a large application portfolio while still allowing application-specific code and authorization changes where required.
